## 2. 逐项核对

### 2.1 预览数量

文件模式的恢复预览质量较高，可作为数据库模式的基准：`LibraryBackupService.RestorePreview.cs:33-46` 会列出备份时间、位置、目标、`视频索引：当前 → 备份`、`搜刮队列：当前 → 备份`、受管文件覆盖/加入/移除数量，并说明「若备份是在软件运行中创建，多个文件可能不是同一时刻的数据」。

缺口：
- 没有数据库模式预览。数据库备份还包含资料文档、审核历史、人物档案、插件设置、AI 作业、图片资产与 `database-export-manifest.json`，这些数量与体积都没有界面呈现。
- 没有「可回退副本将写到哪里」的提示；本分支恢复会生成 `backups/pre-restore-<时间>` 与 `yingge_prev_*` 两层回退，用户无从得知。
- 没有「回退副本需要多少磁盘空间」的预估，而备份前只做硬性空间预检。

### 2.2 风险说明

- 文件模式已有明确风险句（不同时刻、凭据留在凭据管理器、视频原文件不受影响）。
- 数据库模式缺失全部关键风险说明：恢复期间两种存储模式都会被阻断；恢复失败会反向换名；保留的 `yingge_prev_*` 会占用额外空间；中断后需要清理入口。
- 「一致性备份」这一名称在切换到数据库后会产生歧义：文件模式的「一致性」只保证清单字节，不保证多文件同一时刻；数据库模式才真正提供单版本快照。界面必须按模式改写，不能沿用。

### 2.3 进度

- 备份：点击后只有一句「已排定」，没有进度。
- 恢复：只有「正在校验备份并比较当前资料…」一句，随后是模态确认；应用阶段发生在下次启动，界面不再可见。
- 数据库恢复在 30,000 部规模下包含离线校验、可回退副本、暂存导入、换名、复核五个阶段，单句文案不足以让用户判断是否卡死；也没有取消入口。

### 2.4 失败后的操作入口

- 现有实现把异常直接拼进 `BackupInfo.Text`（`MainWindow.xaml.cs:4716`、`4732`），没有「打开日志」「打开备份目录」「重试」「回退到上一版本」入口。
- 数据库恢复失败需要区分三种状态并给出不同入口：
  1. 校验失败（数据库未动）→ 重新选择备份；
  2. 换名前失败（数据库未动，暂存已清理）→ 重试；
  3. 换名后回退失败（库处于 `Blocked`）→ 打开数据目录、查看 `postgres.log`、按文档人工恢复，禁止自动放行文件模式。

## 4. 结论与交付口径

- 发行说明与设置页**不得**出现「数据库备份/恢复已完成」的表述；当前只能写「数据库模式仍为隔离验证，未接入正常启动」。
- 主线集成时必须先修 G1（数据库模式下禁止调用 `LibraryBackupService.StageOfflineBackup` / `StageRestore`），否则会在权威库目录里写旧 JSON 暂存文件，违反「不能暗中继续写旧 JSON」的硬门槛。
- 本审核未运行 GUI，未验证真实鼠标交互；上述结论均来自源码与既有文案，属于只读审核，不是交互验收。
