## 一、每批 6 / 8 / 12 张对照（已实测）

同一隔离库（600 部合成视频）、同一台机器、按 v6 → v8 → v12 交替各跑 2 轮取中位数。

| 指标 | 每批 6 | 每批 8 | 每批 12 | 基线（每批 3） |
| --- | --- | --- | --- | --- |
| 搜索布局 P50 | **395 ms** | 578 ms | 321 ms | 620 ms |
| 搜索完整显示（asyncTotal） | 645 ms | 824 ms | 627 ms | 900 ms |
| 单次停顿 P50 | **45.7 ms** | 68.3 ms | 65.4 ms | ~43 ms |
| 单次停顿最大 | **64.6 ms** | 912.4 ms※ | 192.9 ms | ~74 ms |
| 分类页 60 卡到位 | **1632 ms** | 4349 ms※ | 1557 ms | 2732 ms |
| 滚动 P95 / P99 | 31.8 / 53.2 ms | 25.7 / 29.2 ms | 27.8 / 42.8 ms | 30.0 / 28.4 ms |

※ 标注的两项是同一时段的机器尖峰（v8 那一轮整体被拖慢），不代表批大小本身。

**定档：每批 6 张**。理由是按“优先降低可感知停顿”：6 张的停顿与基线几乎持平（45.7 ms，最大 64.6 ms），同时布局仍快 36%（620→395），分类页 60 卡到位快 40%（2732→1632）。12 张更快但最大停顿 193 ms，明显更易被感知。

卡片数量、分页、选择、海报、分类图 296 节点与 174 条关系线均未改动；诊断里 `graph verified` 仍然通过。

## 二、审核区「暂无搜刮记录」的根因（已修复）

两个原因，第一个是我上一轮的测试数据错了，第二个是真实缺陷。

1. **测试数据错误**：我用 Python 按路径哈希生成 `VideoId`，但路径分隔符/大小写与 C# 的 `IdFor` 不一致，算出的 ID 与索引里的视频对不上，`available.ContainsKey(review.VideoId)` 直接过滤掉记录。用索引里的真实路径重算后记录立刻出现。
2. **真实缺陷（已修复）**：`LoadConfig` 归一化 `DecisionSource` 时只认 `manual / rules / ai`，`plugin` 落进默认分支被改成 `ai`。后果是**每次重启后插件审核记录都会失去来源标记**，审核行因此永远不显示「候选 i/N」下拉——这就是前几轮一直看不到下拉的原因。

修复：把归一化抽成 `NormalizeDecisionSource` 并补上 `plugin`；新增两条回归断言（`decisionSourceKeepsPlugin`、`decisionSourceStillNormalisesOthers`）。`--self-test-plugins` **44/44**。

### 已实测

- 用正确 ID 构造 3 条候选、审核记录指向第 2 条 → 重启后审核行显示「示例作品 2 / 插件: 示例搜刮来源 / EX-002」，下拉显示 **「候选 2/3」**（`shots/review-selector2.png`）。这同时证明「重启后保持」的读取侧正确。
- 记录行同时显示 资料 / 通过 / 否决 三个按钮。

### 未实测

- **切换候选**：真实鼠标点击下拉没有展开（窗口坐标换算不可靠），键盘 Down/Enter 也没能送达弹层；切换写入路径（`ApplyPluginCandidateSelection`）仍只有代码检查。
- **批准 / 否决点击**、**候选写入失败提示**、**清理日志写入失败弹窗**均未取到证据。
- 未做一次真实的「插件页 → 搜刮」点击链路（UIA invoke 在本机多次超时）。
