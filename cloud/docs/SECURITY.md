# 安全边界

## 1. 存什么、不存什么

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 邀请码 | `invites.code_hash` | 仅 SHA-256，明文只在 `admin invite-create` 输出一次 |
| 账号 | `accounts` | 小写账号名、密码哈希、状态、失败计数、锁定截止 |
| 会话 | `sessions` | 令牌 SHA-256、到期、撤销时间、客户端版本、来源 IP |
| 日志元数据 | `error_reports` | 条数、字节数、内容哈希、存储键、保留期 |
| 日志正文 | `/var/lib/yingge-cloud/reports/**.json` | Web 根目录之外，随机文件名 |
| 审计 | `audit_events` | 事件名、账号、IP、少量元数据；**不含正文、口令、令牌** |

从不接收：视频路径、封面、文件名、API Key、完整配置、视频库索引、媒体文件。客户端只把错误事件文字
组成报告；服务端按固定字段白名单二次校验。

## 2. 凭据

- 客户端安装包内**不含** SSH 私钥、数据库口令、对称解密密钥，也没有“隐藏地址”。
- 客户端只保存服务器 HTTPS 地址（`%LOCALAPPDATA%\YinggeVideoLibrary\cloud-account.json`）与
  Windows 凭据管理器中的会话令牌；两者都不足以离线伪造登录。
- 服务端连接串和口令只在 `/etc/yingge-cloud/*.env`（`0600/0640`），不进入仓库、日志或发布包。
- 迁移与运维用 owner 账号，应用进程用 DML-only 账号；两者都不是 `postgres` 超级用户。

## 3. 口令与会话

- 口令使用 ASP.NET Core Identity `PasswordHasher`（PBKDF2-HMAC-SHA512，随机盐，210,000 次迭代），
  不自行发明加密；登录成功时若哈希参数过旧会自动重算。
- 口令策略：12–128 字符，含字母与数字，不等于账号名，拒绝常见弱口令。
- 令牌为 32 字节随机数的 base64url（43 字符），服务端只存 SHA-256；退出、停用、到期即失效。
- 连续 5 次失败锁定 15 分钟；账号不存在时也执行一次等价的哈希校验，响应时间不泄漏账号是否存在。

## 4. 网络

- 只接受 HTTPS：`Security:RequireHttps=true` 时非 TLS 请求返回 426。客户端在非回环地址上拒绝 `http://`。
- Kestrel 只监听 `127.0.0.1:5080`，由 nginx 终止 TLS；只有 `Security:KnownProxies` 中的地址
  可以影响 `X-Forwarded-For/Proto`。
- PostgreSQL 只监听本机 socket，不对公网开放 5432。
- 不跟随重定向、不关闭证书校验；DNS 与证书由系统信任链验证。

## 5. 限速、配额与审计

- 登录 10 次/分钟/IP；注册 5 次/小时/IP；全局 300 次/分钟/IP；上传按会话 3 次/分钟。
- 账号级配额：24 小时 10 份、5 分钟 3 份；超限返回 429 与 `Retry-After`。
- 所有拒绝路径都会写审计（原因、条数索引），但不写正文，也不写 `error_reports`。
- 审计可用于追溯“谁在何时上传/被拒绝/被停用”，但不足以还原日志内容。

## 6. 私密数据的两道闸门

1. **客户端**：上传前用同一套规则把本地路径、UNC、POSIX 路径、媒体文件名、分享链接、签名 URL、
   凭据、邮箱替换为 `<路径>/<文件名>/<链接>/<凭据>/<邮箱>`，并在预览里显示“已脱敏 N 处”。
2. **服务端**：独立再扫一遍；仍命中路径/文件名/链接/凭据则整份拒绝（422 + 第几条），不落盘。

客户端可以被修改，所以服务端的拒绝逻辑不依赖客户端的“防破解”判断；反向也不依赖服务端来判断
用户本机是否安全。

## 7. 保留与删除

- 每份日志默认保留 30 天（`Reports:RetentionDays`），后台任务标记删除并删除文件。
- 用户可在客户端“查看/删除我的上传”里逐份删除；删除后该内容哈希释放，可重新上传。
- 管理员可停用账号（立即撤销全部会话）或撤销邀请码。
- 备份包含账号与日志元数据；备份文件权限 `0600`，保留 30 天。

## 8. 已知残余风险

- 审计记录来源 IP（运维需要），属于个人数据；保留期由备份策略决定，当前未做 IP 匿名化。
- 服务单实例假设：保留期清理未做多实例协调（`for update skip locked` 只能避免重复处理，
  文件删除失败会留下无引用的文件）。
- 上传正文以明文 JSON 存在服务器磁盘：依赖主机访问控制与磁盘加密；未做服务端二次加密。
- 未做 IP 级封禁、WAF、验证码；大规模自动化攻击只能靠限速与监控发现。
- 服务器（Ubuntu 22.04）尚未实际加固与验证，见 `DEPLOYMENT_UBUNTU.md` 第 10 节。

## 9. 事故处置

1. `admin session-revoke --username <账号>` 或 `account-disable` 立即切断访问。
2. 轮换数据库口令：`ALTER ROLE ... PASSWORD`，更新 `/etc/yingge-cloud/*.env` 后重启服务。
3. 若怀疑令牌泄漏：撤销全部会话（停用→启用），客户端会收到 401 并清除本地令牌。
4. 检查 `audit_events` 中 `login.failed/locked/report.rejected` 的时间分布。
5. 需要清除数据时按 `DELETE /reports/{id}` 语义手工标记并删除文件，或从备份恢复后重放保留策略。
